# taskattest (한국어 설명)

**에이전트가 정말로 일을 끝냈는가.** taskattest는 에이전트가 남긴 파일을 **모델 호출 없이** 규칙으로만 검사해 `pass` / `partial` / `fail`로 답하고, 다시 돌려볼 수 있는 증거 번들을 남깁니다.

공개용 영문 설명은 [README.md](README.md)에 있습니다.

## 왜 만들었나

지금 도구들은 에이전트가 **무엇을 했는지**(실행 기록, 토큰, 단계)는 보여 주지만 **결과가 맞는지**는 거의 알려 주지 않습니다. 작업 완수 지표 대부분이 다른 모델에게 판정을 맡기는데, 그러면 비용이 들고 실행마다 결과가 달라지며 감사 자료로 쓸 수 없습니다.

taskattest는 반대로 갑니다. **"끝났다"의 조건을 사람이 먼저 적고**, 도구가 실제 파일과 맞춥니다.

- **결정적 판정.** 같은 입력이면 같은 판정, 같은 증거 digest입니다. 판정 경로에 LLM이 없습니다.
- **로컬 전용.** 데이터가 컴퓨터 밖으로 나가지 않습니다. API 키도, 계정도, 네트워크도 필요 없습니다.
- **의존성 0.** 표준 라이브러리만 씁니다. MCP 서버는 SDK 없이 프로토콜을 직접 구현했고, 엑셀 읽기도 스프레드시트 라이브러리 없이 `zipfile`과 `ElementTree`로 만들었습니다.
- **에이전트가 직접 호출.** stdio MCP 서버로 붙습니다.
- **재현 가능.** 매 실행마다 입력·산출물 해시, 체크별 결과, 재현 명령을 담은 기록을 남깁니다.

## 60초 체험

```bash
git clone https://github.com/sionjang101-create/taskattest && cd taskattest
python -m taskattest --spec examples/agent_says_done/spec.json
```

에이전트에게 미입금 주문 목록을 시켰고 "완료, 미입금 3건"이라고 답했습니다. 3건이 나와야 했고 3건이 나왔습니다.
그런데도 답은 틀렸습니다. 한 건은 지어낸 주문이고 한 건은 빠졌습니다.
[examples/agent_says_done](examples/agent_says_done/README.md)을 보십시오.

## 파일을 읽고 스펙 초안 만들기

스펙을 손으로 쓰려면 먼저 파일을 열어 봐야 합니다. UTF-16 원본 로그라면 그게 가장 오래 걸립니다.
`taskattest draft`가 파일을 읽고 초안을 제안합니다.

```bash
taskattest draft --input orders=in/orders.csv --output picked=out/picked.csv --out spec.json
```

```bash
taskattest draft --trace logs/session01.log --trace logs/session02.log --out spec.json
```

MCP에서는 `draft_spec` 도구가 같은 일을 하고, 필드마다 형식·범위·값 목록을 담은 프로필도 돌려줍니다.
에이전트가 파일을 열지 않고도 자기 조건을 쓸 수 있습니다.

| 대상 | 제안 |
| --- | --- |
| 입력 | 실제 digest로 `file_hash` 봉인 |
| 레코드 산출물 | 필요한 컬럼, 비어 있지 않음, 개별 ID(`id`, `*_id`, `uuid`, `*_no`) 중복 없음, 같은 컬럼이 있는 입력으로 거슬러 확인하는 `subset_of`, 금액류 컬럼 `min: 0` |
| JSON 문서 | 객체로 파싱, 최상위 키, 안에 든 객체 배열에 대한 레코드 체크 |
| 텍스트 | 흔적 없음, 지금 있는 제목을 필수 절로 |
| trace | 줄 접두사, 묶음 필드, 상태 필드, 묶음 80% 이상에 공통인 단계로 `trace_order`, 마지막 단계에 도달한 묶음 수 |

**이 기능이 막으려는 위험.** 에이전트가 자기의 틀린 결과물로 스펙을 뽑으면 그 스펙은 통과합니다.
그래서 초안은 **결과물이 기준을 정하게 두지 않습니다.**

- 개별 ID 중복 없음은 지금 결과물이 중복이든 아니든 제안합니다. 그래야 중복이 실패로 드러납니다.
  `sku`·`barcode` 같은 코드는 물건의 **종류**라 원래 반복되므로, 입력으로 거슬러 확인만 하고 중복 금지는 걸지 않습니다.
- `min: 0`은 컬럼 이름과 **입력**으로 정합니다. 결과물에 음수가 있어도 그걸 잡을 체크가 꺼지지 않습니다.
  입력에 이미 음수(예: 환불)가 있으면 범위를 제안하지 않고 이유를 노트에 적습니다.
- 상한과 trace 불변식은 맞춰 넣지 않습니다. 묶음 수는 관찰된 전부, 즉 가장 엄격한 값으로 두고 기준에 맞게 낮추라고 적습니다.
- 컬럼·키 체크는 파일을 있는 그대로 비춥니다. 에이전트가 빠뜨린 컬럼은 잡지 못하며 노트에 그렇게 적습니다.
  실행 전에, 또는 검증된 예시로 초안을 만드십시오. 정확성은 봉인과 입력 대조 체크가 담당합니다.

초안에는 `"draft": true`가 붙습니다. 사람이 이 표시를 지우기 전까지 모든 판정에 "검토 전 초안" 경고가 들어갑니다.
이미 있는 스펙을 덮어쓰는 초안 생성은 거부합니다.

## 수정 지침 — 무엇이 틀렸나에서 끝나지 않고 무엇을 바꿀지까지

실패한 체크마다 `fix`가 붙습니다. 동작, 파일, 그 동작에 필요한 사실입니다. 에이전트는 문장을 해석하지 않고 바로 고칠 수 있습니다.

수정 지침은 **사실만** 담고, 고치는 방법을 추측하지 않습니다. 판정을 속이는 길이 되지 않게 두 규칙을 둡니다.
입력 봉인이 깨지면 "입력을 원래대로 되돌려라"이지 입력을 고치라는 지침이 아닙니다. trace 체크가 실패하면 "다시 실행하라"입니다.
결과물을 고쳐서는 과정의 실패가 고쳐지지 않기 때문입니다. 수정 지침은 증거 digest 밖에 둡니다.

`test_fixes.py`는 수정 지침만 받는 작은 에이전트로, 심어 둔 실패 두 가지가 지침대로 고치면 모두 통과로 바뀌는 것을 확인합니다.

## 판정 규칙

| 판정 | 조건 |
| --- | --- |
| pass | 모든 체크 통과 |
| partial | 핵심 산출물이 존재하고 일부 체크만 통과 |
| fail | 핵심 산출물이 없거나 통과한 체크가 없음 |

`partial`을 따로 둔 이유는 "파일은 나왔는데 내용이 틀린" 경우가 실무에서 가장 흔하고, 그걸 통과로 처리하면 도구가 무의미해지기 때문입니다.

## 지금 가능한 체크

체크 19종, 다섯 갈래입니다. trace 체크와 범위 검사는 아래 별도 절에 있습니다.

**모든 산출물**

| 종류 | 확인하는 것 |
| --- | --- |
| `file_exists` | 산출물이 실제 파일로 있는가 |
| `file_hash` | 먼저 기록해 둔 SHA-256과 지금도 같은가 |

**레코드 묶음** — CSV, TSV, 엑셀(`.xlsx`·`.xlsm`), JSON 배열, JSONL. JSON 객체 안의 배열은 `records_key`로, 엑셀 시트는 `sheet`(이름 또는 1부터 세는 번호)와 `header_row`로 지정합니다. `target`이 아닌 항목은 자기 이름을 앞에 붙여 씁니다(`source_sheet`, `orders_sheet`). 그래서 **엑셀 산출물을 CSV 입력과 한 체크로 대조**할 수 있습니다.

| 종류 | 확인하는 것 |
| --- | --- |
| `csv_columns` | 필요한 컬럼이 있는가 |
| `row_count` | 건수가 `equals`·`min`·`max`에 맞는가. 범위를 안 주면 "비어 있지 않은가" |
| `unique_key` | 키가 중복되지 않고, 키 없는 레코드가 없는가 |
| `subset_of` | 산출물의 모든 키가 입력에 실제로 있는가 |
| `numeric_range` | 값이 범위 안인가. 개별(`each`) 또는 `sum`·`min`·`max`·`count` 집계 |
| `reconcile_rows` | 한쪽 입력에만 있는 건이 산출물에 정확히 한 번 나오는가(산출물을 믿지 않고 입력에서 다시 계산) |
| `amount_sum` | 합계가 다시 계산한 값과 같은가 |

**JSON 문서**

| 종류 | 확인하는 것 |
| --- | --- |
| `json_valid` | 파싱되는가, 최상위 형태가 기대와 같은가. 산문·마크다운 울타리·잘린 출력을 잡습니다 |
| `json_keys` | 필요한 경로가 있고 지정한 경로가 비어 있지 않은가. `*`는 배열 전체를 훑습니다(`items.*.order_id`) |

**텍스트 산출물**

| 종류 | 확인하는 것 |
| --- | --- |
| `text_contains` | 있어야 할 문구가 있고 없어야 할 문구가 없는가 |
| `no_placeholders` | `TODO`·`lorem ipsum`·`{{`·`I cannot provide` 같은 흔적이 남아 있지 않은가 |

이 중 둘은 **프로그램이 틀리는 방식이 아니라 에이전트가 틀리는 방식** 때문에 있습니다.
`subset_of`는 입력에 없던 그럴듯한 행을 지어낸 것을 잡습니다. `file_hash`는 나머지 체크를
통과시키려고 입력 파일을 몰래 고친 것을 잡습니다.

숫자는 정수 최소 단위로 비교하므로 어디에도 부동소수점 연산이 없고 정밀도는 소수 둘째 자리입니다.
**수행할 수 없는 체크는 실패로 처리합니다.** 기본값으로 통과시키지 않습니다.

## 범위 검사 — 무엇을 남겼나만이 아니라 무엇을 건드렸나

결과물이 맞아도, 시키지 않은 수정이 함께 들어올 수 있습니다. 설정 파일, 잠금 파일, 걸리적거리던 테스트, 다른 모듈의 파일 같은 것들입니다.
같은 20,574건 연구에서 제약 위반은 발견된 문제의 38.33%, 범위 초과는 10.20%였습니다. `scope_changes`는 git 작업 트리를 읽습니다.
바뀐 경로가 선언한 범위 밖이면 실패로 판정합니다.

```json
{"type": "scope_changes", "name": "only billing and its tests", "root": "..",
 "allow": ["src/billing/**", "tests/**"], "deny": ["**/*.lock"]}
```

| 필드 | 뜻 |
| --- | --- |
| `allow` | 작업이 바꿔도 되는 경로 패턴. `*`는 한 폴더 안, `**`는 폴더를 넘음 |
| `deny` | `allow`에 걸려도 절대 바꾸면 안 되는 경로 |
| `ignore` | 판정에서 아예 빼는 경로 |
| `root` | 판정할 폴더, 스펙 기준 상대 경로(`.taskattest/` 안의 스펙이면 `..`) |
| `base` | 비교할 git 기준, 기본 `HEAD` |
| `max_changed` | 바뀐 파일 수의 상한 |

다음을 모두 변경으로 셉니다.
- 수정한 파일
- 추가한 파일
- 삭제한 파일
- 새로 만든 미추적 파일

다음은 세지 않습니다.
- git이 무시하는 파일
- `.taskattest/` 아래 파일

바뀐 파일마다 내용 해시를 기록합니다. 수정 지침은 범위 밖 파일을 하나씩 나열하고 되돌리는 방법을 알려 줍니다(기준에서 복원, 새 파일은 삭제).
그리고 스펙을 고치지 말고 사람에게 물으라고 지시합니다.

사람이 아직 커밋하지 않은 작업은 에이전트가 한 일이 아닙니다. 관문의 시작 훅(아래)을 붙이면 세션을 시작할 때 이미 바뀌어 있던 경로를 해시와 함께 기록합니다.
기록된 경로는 판정에서 뺍니다. 에이전트가 그 파일을 더 바꾼 경우에만 셉니다. 사람의 미완성 수정을 에이전트가 되돌려 버린 경우도 변경으로 보고합니다.

## 행동 기록(trace) — 결과물만이 아니라 무엇을 했는가

결과물 체크는 파일이 맞는지 묻습니다. 그런데 에이전트와 로봇의 실패는 과정에서 많이 납니다.
금지된 행동을 했다가 되돌렸거나, 순서를 어겼거나, 충돌했다가 우연히 복구한 경우입니다.
trace 체크는 시간순 상태 기록을 읽어 과정을 판정합니다.

| 종류 | 확인하는 것 |
| --- | --- |
| `trace_always` | 모든 시점에(또는 `when`이 성립하는 시점마다) 불변식이 지켜졌는가 |
| `trace_eventually` | 언젠가 한 번은 일어났는가 |
| `trace_final` | 마지막 시점이 조건을 만족하는가 |
| `trace_count` | 일치한 시점 수, 그 상태로 들어간 횟수(`edges`), 필드의 서로 다른 값 수(`distinct`) |
| `trace_order` | 정해진 순서로 일어났는가 — 기록 전체에서, 또는 작업이나 재시도 묶음마다(`group_by`) |

기록은 JSONL, JSON 배열, CSV, 또는 원본 로그입니다. `line_prefix`를 주면 그 접두사로 시작하는 줄만
레코드로 읽어서, 러너가 쓴 로그를 그대로 판정할 수 있습니다. UTF-16 로그는 BOM으로 알아봅니다.
`target`에 파일 여러 개를 순서대로 줄 수 있습니다.

**조건은 코드가 아니라 데이터입니다.** 스펙 안의 어떤 것도 실행되지 않습니다.

```json
{ "all": [
    { "field": "phase", "eq": "commit" },
    { "within": { "fields": ["pos.x", "pos.y"], "point": [1.0, 2.0], "radius": 0.05 } }
] }
```

연산자는 `eq`, `ne`, `lt`, `le`, `gt`, `ge`, `in`, `startswith`, `exists`이고 `all`, `any`, `not`으로
묶습니다. `within`은 거리이며 제곱으로 비교해 제곱근을 쓰지 않습니다. 숫자는 텍스트에서 읽은
십진수로 비교합니다. 없는 필드는 어떤 비교도 만족하지 않고, 0개 시점에 대해 확인한 불변식은
실패하며, 모르는 연산자는 조용히 거짓이 되지 않고 오류가 됩니다.

**trace 체크에는 최종 상태 체크를 짝지어 두십시오.** 로그는 어떤 행동이 일어났다고 기록했는데
나중에 다른 무언가가 그 결과를 되돌렸을 수 있습니다. 로그는 행동을 기록하고, 결과는 최종 상태만
기록합니다. 둘 다 요구하십시오.

## 엑셀을 어떻게 읽는가

`.xlsx`는 XML을 담은 ZIP입니다. 그래서 [xlsx.py](xlsx.py)가 `zipfile`과 `ElementTree`만으로 읽습니다. 스프레드시트 라이브러리를 쓰지 않습니다.

처리하는 것: 공유 문자열(서식 런으로 쪼개진 값 포함), 인라인 문자열, 불린, 수식 결과, `#DIV/0!` 같은 오류 셀, XML에서 생략된 셀(컬럼이 헤더와 어긋나지 않게), 지수 표기 정규화(부동소수점 연산 없이), 1900·1904 두 기준의 날짜·시간을 ISO 8601로 변환.

하지 않는 것: 쓰기, 수식 자체(캐시된 결과를 읽습니다), 병합 셀, 차트, 피벗. 값은 **저장된 대로** 읽고 표시 형식대로 읽지 않습니다. 엑셀이 만들어 낸 존재하지 않는 날짜 1900-02-29는 날짜로 꾸미지 않고 숫자로 남깁니다.

## Claude Code 플러그인

이 저장소는 Claude Code 플러그인이면서 그 자체로 마켓플레이스입니다. 플러그인 안에 패키지 소스가 들어 있어서 pip로 설치할 것이 없습니다.
파이썬 3.10 이상만 있으면 됩니다.

```text
/plugin marketplace add sionjang101-create/taskattest
/plugin install taskattest@taskattest
```

| 구성 | 하는 일 |
| --- | --- |
| 멈춤 훅 | 에이전트가 끝내려 할 때 완료 관문 실행 |
| 세션 시작 훅 | 범위 검사를 위해 이미 있던 미커밋 작업을 기록 |
| MCP 서버 | `verify_task`, `replay_evidence`, `draft_spec`, `describe_checks`. 프로젝트 폴더 안으로 제한 |
| `define-done` 스킬 | 사람과 함께 `.taskattest/spec.json` 작성: 결과물이 무엇인지, 무엇을 바꿔도 되는지 |

스펙이 없으면 훅은 아무것도 하지 않습니다. 작업에 끝남의 정의가 생기기 전까지 플러그인은 조용합니다.

`python3`가 실제 파이썬이 아니라면 플러그인의 `python` 옵션을 설정하십시오. 윈도에서는 스토어 안내 프로그램인 경우가 많습니다.
이때는 `python`이나 `python.exe` 전체 경로를 쓰면 됩니다. 파이썬을 실행하지 못하면 훅은 에이전트를 막지 않고 실패만 합니다.

Claude Code 2.1.325에서 확인했습니다. 체크아웃에서 플러그인을 불러온 것(`--plugin-dir`)이고, 마켓플레이스 설치로는 아직 확인하지 않았습니다.

헤드리스 실행에서 에이전트에게 끝남을 정의하고(`src/billing`과 `tests`만 변경 가능) 버그를 고치라고 시켰습니다. 에이전트는 다음 순서로 진행했습니다.
1. 스킬을 불렀습니다.
2. `describe_checks`와 `verify_task`를 썼습니다.
3. 스펙을 작성했습니다.
4. 범위 안에서 버그를 고쳤습니다.
5. 멈춤 훅을 통과했습니다.

윈도에서 기본값 `python3`로 두었을 때는 의도한 대로 훅이 실패하고 세션은 계속됐습니다.

에이전트가 쓴 스펙에는 파일 확인과 범위 검사만 있었고 테스트를 실행하는 검사는 없었습니다. 명령을 실행하는 검사가 아직 없기 때문입니다.

## 코딩 에이전트 완료 관문

코딩 에이전트의 "끝났다"는 주장입니다. 관문은 에이전트가 멈추기 전에 그 주장을 확인합니다.
실제 코딩 에이전트 세션 20,574건 분석에서, 발견된 문제의 22.58%는 에이전트가 자기 작업 상태를 잘못 보고한 것이었고,
해결된 문제의 91.49%는 개발자가 직접 반박해야 했습니다([arXiv 2605.29442](https://arxiv.org/html/2605.29442v1)).
관문은 그 반박을 규칙으로 합니다.

끝남의 정의를 `.taskattest/spec.json`에 두고(`taskattest draft`로 초안을 만든 뒤 검토), 관문을 멈춤 훅으로 붙입니다.
Claude Code라면 `.claude/settings.json`에:

```json
{
  "hooks": {
    "SessionStart": [{ "hooks": [{ "type": "command", "command": "taskattest gate start", "timeout": 60 }] }],
    "Stop": [{ "hooks": [{ "type": "command", "command": "taskattest gate", "timeout": 60 }] }]
  }
}
```

| 에이전트가 멈추려 할 때 | 관문 |
| --- | --- |
| `.taskattest/spec.json` 없음 | 멈춤 허용. 끝남의 정의가 없는 것은 실패가 아닙니다 |
| 스펙 통과 | 멈춤 허용, 증거 번들 남김 |
| 스펙 실패 | 멈춤을 막고, 실패마다 구조화된 수정 지침을 사유로 전달 |
| 같은 실패가 세 번째 | 더 막지 않고 증거와 함께 사람에게 알림. 고치지 못하는 에이전트를 가두지 않습니다(`TASKATTEST_GATE_REPEATS`로 조정) |

`taskattest gate start`는 `scope_changes` 체크가 있을 때만 의미가 있습니다. 세션 시작 시점에 이미 있던 미커밋 작업을 `.taskattest/baselines/`에 기록해서, 그 작업을 에이전트 탓으로 돌리지 않게 합니다. 재개하거나 압축한 세션은 처음 기준선을 유지합니다. 기준선은 프로젝트 안에 있습니다. 따라서 실수와 범위 초과는 막지만, 기준선을 일부러 고쳐 쓰려는 에이전트까지 막지는 못합니다.

Claude Code 2.1.325 헤드리스 모드로 확인했습니다. 틀린 결과물을 확인 없이 "done"이라 답하라고 시킨 에이전트가 막혔고,
수정 지침대로 지어낸 행을 지우고 빠진 행을 넣은 뒤 두 번째 관문 실행에서 pass로 멈췄습니다.
Codex와 Cursor에도 멈춤 훅이 있지만 아직 시험하지 않았습니다.

범위 검사도 같은 방식으로 시험했습니다. 범위가 `src/billing/**`와 `tests/**`인 일회용 저장소를 썼습니다.

첫 실시간 실행에서 오탐이 드러났습니다. 세션 전부터 있던 파일을 에이전트가 바꾼 것으로 판정했습니다.
에이전트는 그 파일을 지우지 않았고, 관문은 사람에게 넘겼습니다. 시작 훅 기준선은 이 오탐을 고치려고 넣었습니다.

고친 뒤에는 두 경우를 시험했습니다.
- 결제 버그만 고치라고 시킨 에이전트는 통과로 멈췄습니다.
- `pyproject.toml` 버전도 올리라고 함께 시킨 에이전트는 두 곳을 모두 고쳤고 관문에 막혔습니다.
  스펙을 고치지 않았고, 사람이 요청한 수정을 임의로 되돌리지도 않고 사람에게 선택을 물었습니다. 관문은 같은 실패가 세 번째일 때 사람에게 넘겼습니다.

두 번째 경우는 요청으로 유도한 것이고, 실제 사용 중에 관찰한 것은 아닙니다.

## MCP 연결 — 에이전트가 자기 일을 스스로 검사한다

taskattest는 [Model Context Protocol](https://modelcontextprotocol.io)을 stdio로 말합니다. 사람이
나중에 CLI를 돌리는 대신, **에이전트가 자기 완수 주장을 직접 검사**할 수 있습니다.

```bash
taskattest-mcp --root /허용할/절대경로
```

| 도구 | 하는 일 |
| --- | --- |
| `verify_task` | 스펙 파일로 판정. 판정·증거 digest·체크별 내역을 돌려줍니다 |
| `replay_evidence` | 기록된 manifest를 다시 돌려 digest가 그대로인지 봅니다. 주장된 판정을 믿는 대신 **시험하는** 쪽입니다 |
| `draft_spec` | 파일을 읽고 스펙 초안과 필드 프로필을 돌려줍니다. 초안은 표시되며 검토 전까지 경고가 붙습니다 |
| `describe_checks` | 체크 종류와 스펙 템플릿을 돌려줍니다. 에이전트가 스펙을 쓰기 전에 부릅니다 |

MCP 클라이언트에 등록하면 됩니다. Claude Code나 Claude Desktop이라면 이렇게 씁니다.

```json
{
  "mcpServers": {
    "taskattest": {
      "command": "taskattest-mcp",
      "args": ["--root", "/허용할/절대경로"]
    }
  }
}
```

**SDK를 쓰지 않았습니다.** 프로토콜을 직접 구현해 표준 라이브러리만 씁니다. 설치할 것이 여전히
없습니다. 한 프로세스가 두 세대를 다 받습니다. 최신 `server/discover` 방식(2026-07-28)과 기존
`initialize` 방식(2025-11-25 이전)입니다.

**`--root`를 주십시오.** 스펙은 읽을 파일을 지정합니다. `--root`를 주면 그 디렉터리를 벗어나는
경로는 거부됩니다. 스펙 안의 참조를 따라간 경로까지 막습니다. 주지 않으면 이 프로세스가 읽을 수
있는 것은 다 읽습니다.

최신 규격에서 한 가지는 의도적으로 느슨하게 뒀습니다. 요청마다 붙는 `_meta`는 클라이언트가
`server/discover`를 먼저 던진 뒤에만 요구합니다. `initialize`로 들어온 클라이언트에게는 강제하지
않습니다. 그 방식만으로는 최신 방언을 쓴다는 근거가 되지 않기 때문입니다.

## 검증한 것과 아직 아닌 것

**검증:** 윈도·파이썬 3.11.15와 3.12.10에서 열 묶음 **217개 항목 전부 통과**했습니다. 두 버전 모두입니다. CI가 같은 열 묶음을 리눅스·맥·윈도와 파이썬 3.10·3.12·3.13에서 돌리고, 빌드한 wheel이 다른 것 없이 단독으로 설치되는지도 확인합니다.

- `selftest.py`(19개): CSV 대조와 JSON+보고서 산출물. 다섯 경우 판정이 기대와 일치하고 반복 실행 digest도 일치합니다. 일부러 망가뜨린 산출물에서 심어 둔 결함 일곱 개가 각자 자기 체크에 잡히고 그 밖에는 실패하지 않습니다.
- `test_xlsx.py`(25개): XML을 손으로 적은 워크북으로 까다로운 셀마다 리더가 무엇을 돌려주는지 정확히 확인하고, 이어서 엑셀 산출물을 CSV 입력과 대조하는 업무 한 건을 끝까지 판정합니다.
- `test_trace.py`(29개): 조건 언어, 잡음 줄이 섞인 UTF-16 원본 로그로 판정한 여러 단계 작업 — 정상 실행은 모든 trace 체크를 통과하고 결함 실행은 그 결함을 노린 체크만 실패 — 실패 기본값, 목록 target의 `--root` 제한.
- `test_draft.py`(33개): 초안이 무엇을 제안하고 무엇을 거부하는가 — 틀린 결과물(중복 ID, 지어낸 주문, 음수 금액)은 자기 초안에서도 실패, 코드는 중복 금지를 걸지 않음, 입력에 환불이 있으면 범위를 빼고 이유를 적음, trace, 결정성, 덮어쓰기 방지.
- `test_plugin.py`(13개): 플러그인 매니페스트와 패키지 버전 일치, 훅 둘과 MCP 항목이 설정한 파이썬으로 실행기를 부름, 실행기가 스펙 없으면 허용·실패 스펙은 차단·고치면 통과, MCP 서버 시작, CLI 전달.
- `test_scope.py`(31개): 경로 패턴 규칙, 범위 밖 수정·추가·삭제를 되돌리는 방법과 함께 보고, deny 우선, 무시 경로, 하위 폴더 기준, 한글 파일 이름, 스펙 오류, `--root` 차단, 세션 기준선(기존 작업 제외, 추가 수정과 되돌림 적발, 재개 시 유지), 관문 차단 후 통과.
- `test_gate.py`(10개): 멈춤 훅 규약 — 스펙 없으면 허용, 실패는 수정 지침과 함께 차단, 같은 실패 세 번째는 사람에게 넘김, 고치면 통과, 실행마다 증거.
- `test_fixes.py`(9개): 수정 지침만 따르는 에이전트가 심어 둔 실패 두 가지를 모두 통과로 바꾸고, 지침이 입력 수정이나 과정 실패 덮기를 시키지 않음.
- `test_examples.py`(8개): 60초 예제가 README에 적힌 출력을 정확히 내는지, 입력 봉인이 어느 플랫폼에서 받아도 유지되는지.
- `test_mcp_server.py`(40개): 서버를 실제 하위 프로세스로 띄워 두 세대 핸드셰이크, 도구 4개, 오류 규약, 증거 재현, `--root` 거부, 초안 경고를 포함한 `draft_spec`을 확인합니다.

패키지 자체는 **주장이 아니라 설치로** 확인했습니다. wheel을 빌드해 깨끗한 가상환경에 설치하고 저장소 밖에서 실행했습니다. 그 환경의 `pip list`에는 `pip`과 `taskattest`뿐이고, 콘솔 스크립트 두 개와 MCP 핸드셰이크가 그 설치본에서 동작합니다.

**아직:** 큰 용량, 리눅스·맥, 동시 실행, BOM 외의 인코딩. 그리고 **엑셀이 직접 저장한 파일**입니다. 리더는 규격에 맞게 작성한 XML로 검증했고, 엑셀이 저장한 실제 파일로는 아직 확인하지 않았습니다.

## 유료 계획을 미리 밝힘

MCP 연결, 체크 확장, 엑셀 읽기는 붙였습니다. 다음은 리눅스·맥에서의 테스트 실행, 엑셀이 직접 저장한 워크북 확인, 큰 용량 처리, 시트 전체를 메모리에 올리지 않는 스트리밍입니다.

유료는 **여러 사람·여러 실행의 감사 기록, 승인 이력, 지난 증거와 비교, CI 보고** 같은 팀 기능으로 계획합니다. 이 문서에 적힌 기능은 계속 무료이고 Apache 2.0입니다. 유료는 별도 비공개 추가 구성이며, 이미 공개한 것을 거두어 가지 않습니다.

## 비슷한 프로젝트

**[taskproof](https://github.com/HaoHaoP/taskproof)** 는 이 프로젝트와 무관한 별개 프로젝트이고,
이쪽보다 먼저 공개됐습니다. 전제가 거의 같습니다. 에이전트가 끝냈다는 자기 주장을 믿지 않는다는 것입니다.
그쪽은 코딩 에이전트에 작업을 배포하고, 사용자가 준 **수락 명령**을 돌려 그 종료 코드로 판정합니다.
작업 트리가 실제로 바뀌었는지 확인하고, 금지 경로를 막고, 원장을 남깁니다. 웹 보드와 읽기 전용 REST API,
데스크톱 콘솔도 있습니다.

**그쪽 소스를 읽어 보고 내린 결론은, 경쟁이 아니라 서로 맞물린다는 것입니다.**
그쪽은 종료 코드로 판정합니다. 이쪽은 **판정에 쓸 만한 종료 코드 그 자체**입니다.

```toml
[[taskgroup]]
id = "reports"
project = "reports"
verify = "taskattest --spec .taskattest/spec.json"
verify_kind = "check"
```

[examples/with_taskproof](examples/with_taskproof/README.md)를 보십시오. 그쪽 문서의 설정 형식을 따른 것이고, taskproof 안에서 실제로 돌려 보지는 않았습니다.

이쪽이 더하는 것은 이렇습니다.

- **손으로 쓴 명령 대신 타입 체크.** 수락 명령은 작성자가 떠올린 것만 잡습니다. `subset_of`는 입력에
  없던 레코드를, `file_hash`는 나머지 체크를 통과시키려 고친 입력을 잡습니다. 누가 미리 떠올렸는지와
  무관하게 잡힙니다.
- **산출물을 열어 봅니다.** CSV, TSV, 엑셀, JSON, JSONL. 그쪽은 파일 내용을 읽지 않습니다. 파일이
  바뀌었는지는 보지만 내용이 맞는지는 보지 않습니다.
- **재현되는 증거.** digest는 입력·산출물·체크·판정에 대해 내용 주소화되고 타임스탬프와 실행 ID를
  제외합니다. 그래서 같은 입력이면 어느 기계에서도 같은 digest가 나오고 `replay_evidence`가 다시
  도출합니다. 그쪽의 트리 digest는 크기와 수정 시각으로 만들어집니다. 변경 감지기이지 증거가 아닙니다.
- **MCP.** 에이전트가 작업 중에 직접 호출합니다. CLI 어댑터로 감싸이는 쪽이 아닙니다.
- **순수 파이썬.** 그쪽 수락 명령은 `/bin/sh`를 거칩니다.

**그쪽에 있고 이쪽에 없는 것:** 작업 배포, 작업 트리 격리, 동시 실행, 금지 경로 강제, 작업 원장,
에이전트 어댑터, 보드, 데스크톱 앱. 그쪽은 시스템이고 이쪽은 검사 엔진입니다.
시스템이 필요하시면 그쪽을 쓰시고, 그 수락 명령을 이쪽으로 향하게 하시면 됩니다.
